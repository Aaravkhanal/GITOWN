# GITOWN product scope and parity decisions

This is the product decision record for gaps raised against `BLUEPRINT.md`. It narrows the blueprint into a product GITOWN can operate safely; it is not a commitment to reproduce every GitHub feature. The shipped feature ledger remains [Product phases](PRODUCT_PHASES.md), operational blockers remain [Release gates](RELEASE_GATES.md), and the technical sequence remains [Roadmap](ROADMAP.md).

## Product identity

GITOWN is an independent, Git-compatible home for projects that combines portable repositories, safe collaboration and review, approachable browser/CLI workflows, and public project discovery. Its distinctive promise is that Git data remains ordinary Git data and users can move their source without being locked into GITOWN. Familiar forge conventions are useful; feature-count parity is not the goal.

The product is successful when a small team can host code, collaborate on it, protect important branches, understand a project's activity, and take its repository elsewhere. It is not required to provide every enterprise, social, registry, or CI feature to keep that promise.

## Decisions

| Capability                               | Decision                                                                           | Scope and reason                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser binary editing                   | **Defer full editing; consider bounded binary upload as a Phase 2.1 improvement.** | A browser editor is primarily for source/text. Arbitrary binary editing is misleading and unsafe. If added, upload/replace must be a normal Git commit with size/quota, branch-rule, MIME-sniffing, and audit checks; never render active content inline. Git clients remain the supported path for large/binary work.                                                                                                                                     |
| Repository import/export                 | **Essential, staged.**                                                             | Portability is part of GITOWN's identity. Keep the current public-forge import and Git bundle export; next deliver a guided import preview and a documented round-trip export package. Preserve refs and useful metadata, exclude credentials/secrets, and prove an exported repository can be re-imported.                                                                                                                                                |
| Authenticated/private forge import       | **Essential after the safe public-import UX; not an arbitrary-URL feature.**       | Users need a way to bring their own private projects. Start with explicitly supported providers and read-only, narrowly scoped OAuth/deploy credentials. Never accept credentials embedded in URLs or run an import against an unvalidated destination. Encrypt temporary credentials, redact them, audit access, and delete them when the job ends or is cancelled. Provider-specific scope and SSRF controls are required before enabling each provider. |
| Organizations and teams                  | **Basic shared ownership is essential; enterprise parity is not.**                 | Districts and crews already provide baseline organization/team concepts. Prioritize lifecycle and understandable administration (transfer, archive/close, member/crew management, clear permission summaries). Defer SAML/OIDC, SCIM, IP allowlists, compliance exports, and deep enterprise policy until real organizational pilots demand them.                                                                                                          |
| Forks and cross-repository pull requests | **Current remix-family model is sufficient for the first product boundary.**       | Remixes and cross-project Unite requests inside one family exist. Open-ended fork networks, upstream synchronization, and arbitrary cross-owner PRs add complex visibility, object-copy, abuse, and deletion semantics. Defer until pilot usage demonstrates a concrete collaboration need; retain clone/push and bundle portability meanwhile.                                                                                                            |
| Package registries                       | **Releases/assets are core; standards-complete registries are not.**               | Drops and downloadable assets meet the initial release need. The current crate/npm/OCI subsets must be described as experimental and must not claim general client compatibility. Do not expand ecosystems until one is selected from user demand and passes official-client conformance, auth, immutability, quota, malware/abuse, and storage tests.                                                                                                     |
| Hosted CI / Routes execution             | **Not essential to GITOWN's initial identity; remain disabled.**                   | Routes may plan work and record status, but no repository-authored command may run. Do not ship hosted CI until an independently reviewed sandbox enforces isolation, secrets, live quotas, network policy, cancellation, cleanup, and multi-tenant boundaries under hostile tests. Users can connect external CI through webhooks and commit statuses.                                                                                                    |
| Public profiles and discovery            | **Core differentiator, bounded by privacy.**                                       | Keep opt-in public profiles, project showcases, topics, and discovery. Private/internal repository metadata must never leak through ranking, search, feeds, or profile aggregation. Do not optimize social engagement at the cost of repository privacy or moderation capacity.                                                                                                                                                                            |
| Billing and enterprise identity          | **Explicitly out of current scope.**                                               | Pledges remain non-charging. Do not collect card details or add enterprise identity without a separate product, compliance, and security decision.                                                                                                                                                                                                                                                                                                         |
| High availability                        | **Operational evolution, not parity checkbox.**                                    | Start with a verified private single-node pilot. Define service objectives, budget, and recovery objectives from actual use before selecting HA architecture. No distributed storage or multi-region promise before failover and restore drills prove it.                                                                                                                                                                                                  |

## Ranked implementation sequence

### S0 — Pilot evidence before broader onboarding

Complete the actual private-host setup, verified-email SMTP test, alert delivery test, encrypted off-host backup, and isolated restore drill. Obtain an independent security review and close or explicitly accept high-risk findings. Run measured failure/load exercises and set pilot account/repository limits. These are release gates, not feature work; see [Private pilot](PRIVATE_PILOT.md) and [Release gates](RELEASE_GATES.md).

### S1 — Portability and everyday project operations

1. **Shipped:** guided preview for supported public providers, with canonical source/destination, visibility, no-credential disclosure, and the current shallow/default-branch limitation. The preview validates URL structure and current DNS answers but does not verify repository existence; import repeats DNS resolution, so rebinding remains a documented pilot risk.
2. **Shipped:** a versioned export tar alongside the existing raw Git bundle route. The v1 manifest contains source repository display metadata, default branch, refs, size and SHA-256, plus explicit exclusions. It never exports credentials or collaboration access state.
3. **Shipped:** browser restore of GITOWN export packages and an automated PostgreSQL/real-Git round-trip test. It compares manifest refs to the bundle, validates the default branch, enforces size/quotas, and rejects corrupt archive input. Do not describe this as a full application backup: issues, reviews, memberships, settings, and secrets are not portable yet.
4. **Next:** after the public path is well tested, implement provider-specific private import using OAuth or narrowly scoped read-only credentials, an isolated background job, secret deletion, auditing, DNS/redirect/egress defenses, cancellation, and authorization-denial tests. Enable one provider at a time.
5. **Shipped, bounded:** the browser can add a binary blob up to 512 KiB as an ordinary Git commit. It uses expected-head conflict checks, repository write/branch-rule policy, MIME sniffing, and an audit event. Text/active content stays on the text path or is rejected; larger assets use Git/LFS. Binary editing in a browser canvas is not planned.

### S2 — Team collaboration that makes districts dependable

Pilot lifecycle safeguards now include clear member/crew removal confirmations, permission-loss consequences, server-side crew branch-rule dependency checks, and audit records. Existing roles and owner-only policy changes remain in force. Still open for pilot evidence: recoverable district archive/closure, repository ownership transfer between personal and district ownership, and a consolidated administrative audit export. These alter long-lived ownership/access state, so define restore behavior, approval authority, and repository effects with pilot operators before implementing them. Do not start SAML/OIDC or SCIM as part of this slice.

### S3 — Demand-led ecosystem choices

Use pilot evidence to choose at most one next ecosystem investment: broaden remix collaboration/upstream sync, or make one package ecosystem genuinely interoperable. Define a client compatibility suite before implementation. Keep Routes command execution disabled until its sandbox release gate passes; no schedule pressure overrides this boundary.

### Later / requires separate decision

Open fork networks and arbitrary cross-owner PRs; full npm or OCI registry compatibility; additional package formats; SAML/OIDC/SCIM and compliance features; billing; hosted CI; multi-region/high-availability service. Each needs an owner, user evidence, threat-model update, operational budget, migration/export path, and a separate acceptance gate before work starts.

## Completion rule

Do not label a slice complete because an endpoint or screen exists. Require authorization and denial tests, API and UI behavior where applicable, audit/observability, failure and recovery coverage, documentation, and a tested data-export path. Update [Product phases](PRODUCT_PHASES.md) and [Status](STATUS.md) to the actual boundary in the same change. A deferred item is not a defect when the decision and supported alternative are explicit.
